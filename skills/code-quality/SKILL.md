# Code Quality（代码质量审查与优化）

在请求范围内提高代码质量：按证据判断问题，选择收益明确的改进，保持与任务相称的改动和验证成本。代码已经足够清晰可靠时，可以不改。

## 确定动作与范围

- **审查模式**：用户要求“审查 / 检查 / 评估”时，只读分析并输出发现，不修改代码。
- **修改模式**：用户要求“优化 / 清理 / 重构 / 修复”时，在授权范围内直接修改并验证；遵循“仅建议”“先审查”等明确限制。单独调用且意图不明时先只读检查。
- 从请求、选中代码及对话上下文确定范围，先检查仓库约定和当前差异；只有影响范围或目标的实质歧义才询问，不把缺省范围解释为整个项目。
- 大型范围先建立模块清单，优先关键路径、已知问题和近期变更，再分批推进。区分完整检查、抽样和未检查部分；已获授权的批次无需逐批重复确认。
- 先理解输入输出、调用方、数据流及现有测试。只读取影响当前判断的上下游；范围外发现单独报告，保留用户已有修改。

## 审查与决策

每个发现先确认：**触发条件是什么，证据在哪里，对谁有何影响，收益是否值得风险，能否更小地修改？** 区分已确认问题和待验证假设，不把个人风格偏好当缺陷。

按代码和任务选择相关维度，不为填写清单而制造问题：

| 维度 | 判断重点 |
| --- | --- |
| 正确性与健壮性 | 契约、边界、错误传播、状态一致性及适用的并发问题；处理真实输入和信任边界，不堆叠无依据的兜底或静默吞错 |
| 简洁与可读性 | 减少不必要的分支、状态、嵌套和间接层；命名表达意图，注释解释原因；不以行数更少替代可理解性 |
| 冗余与复用 | 删除前核实导出、注册、配置、反射或其他动态调用，不能仅凭文本搜索无引用判定死代码；优先已有抽象，共同语义和变化原因一致时才提取复用 |
| 可维护性 | 职责和依赖边界清晰；不为假想需求增加通用框架，不把不同业务规则仅因形似而耦合 |
| 性能与资源 | 关注实际负载下的重复工作、复杂度、I/O、阻塞、分配和资源释放；只有涉及性能、内存优化或发现相关问题时，读取 [性能与内存参考](references/performance-memory.md) |

优先级由**实际影响、触发可能性和紧迫性**决定，与问题所属维度分开：

| 级别 | 含义 |
| --- | --- |
| P0 | 已确认且需立即处理的严重故障、数据损坏或安全问题；说明影响范围与紧急依据 |
| P1 | 对关键路径、常见使用或资源预算有显著影响，应优先处理 |
| P2 | 影响局部、非紧急但有明确价值的问题或维护改进 |
| P3 | 可选的细节改进；纯风格偏好通常省略 |

严重程度不替代修改授权；证据不足的假设单列，说明需要什么证据，不包装成确定缺陷。

## 修改与兼容

- 围绕一个清晰目的小步修改，便于审阅和定位回归；避免夹带无关格式化、依赖新增或升级，以及 lint、构建等配置调整。
- 纯重构保持公开接口和可观测行为，包括返回值、异常类型与消息、日志、副作用及其顺序；不能为缩短代码改变输入可变性或共享状态语义。
- 在修复授权内，以需求、测试或调用方契约确定缺陷的预期行为，说明行为变化并补充相应验证；契约不清时先澄清，不自行决定新的业务规则。相关文档随已授权的行为变化更新。
- 看不懂或无法确认用途的代码先保留并继续查证。新抽象、缓存或并发应有当前需求和明确收益，不能只为“更优雅”引入复杂度。

## 按风险验证

- 使用项目现有测试、类型检查、lint 或构建命令，先验证受影响部分，再按影响扩大；优先记录相关基线，区分原有失败与本次引入的失败。
- 低风险清理使用差异检查和相关静态检查即可；修改关键逻辑、边界或缺陷时，补充或运行能暴露回归的针对性测试。测试断言行为，不照抄实现或锁死内部结构。
- 没有测试框架时使用可复现的最小执行检查，记录输入、预期和实际结果。关键路径缺乏可信验证条件时暂缓高风险修改，并说明缺失条件；手动走通正常路径不能证明并发或异常路径正确。
- 性能和内存结论遵循参考文档中的测量要求。无法执行时明确区分静态推断、建议验证和实际运行结果，不声称已通过或已提升。
- 检查最终差异是否仍在范围内；相关检查通过且无新增疑点后结束，不反复扩大清理或测试范围。

## 交付

- **审查**：先给结论及覆盖范围，再按优先级列出有行动价值的发现：`[文件:行] [级别] 问题、触发条件与影响 → 证据 → 建议`。没有发现时直接说明，不作全局无缺陷保证。
- **修改**：概括实际改动及原因，指出关键位置、已授权的行为变化和必要取舍；相同目的的改动可合并描述，无需逐行复述差异。
- 集中报告验证命令或方法、结果，以及必要的未处理项及原因；明确哪些检查未执行。性能数据同时给出测量条件，待验证假设与已确认结果分开。

审查原则参考：[Google 代码审查指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)与[审查标准](https://google.github.io/eng-practices/review/reviewer/standard.html)。
