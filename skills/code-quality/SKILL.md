# Code Quality（代码质量审查与优化）

对代码执行质量审查与主动优化（用户反复强调的硬性要求）：简洁高效、鲁棒健壮、易于维护，且**不破坏已有功能**。

"不破坏已有功能"的默认含义：不改公开 API 签名、不改可观测行为（返回值、错误消息格式、日志输出、副作用顺序），除非用户明确要求。

## 工作流

### 0. 确定范围
- 范围大（如"整个项目"）时：先抽样审查核心模块，汇报总体发现与分级，再按用户确认的顺序分批处理
- 范围不清时先问，不要默认全量动手

### 1. 先理解，后动手
- 一句话概括这段代码做什么；输入的坑（空值、越界、异常格式）；改动影响哪些上下游（blast radius：调用方、测试、配置、文档）
- 看不懂的代码只标记、不删除

### 2. 审查（每个发现先自我质疑）
每个发现先问自己：这是真问题还是风格差异？修复收益是否大于改动风险？有没有更小的改法？

按优先级检查（高优先级问题必须处理，低优先级仅在有把握时处理）：

| 优先级 | 类别 | 内容 |
|---|---|---|
| P0 | 正确性/安全 | 空值/越界/异常输入/并发缺陷；注入、硬编码敏感信息（按需加固，不过度防御） |
| P1 | 简洁 | 死代码、无用变量/导入、冗余分支、重复逻辑、过度设计 |
| P2 | 可维护 | 命名准确、职责单一、提取公共逻辑、依赖清晰 |
| P3 | 可读 | 魔法数字、嵌套过深、注释与代码不一致 |

### 3. 优化 + 验证
- **小步改**：一次只处理一类问题；保留原逻辑，每步可回滚对比
- **必验证**，验证结果必须写明方式，不接受"已验证"三个字：
  - 有测试？跑测试并报告结果（如"pytest 通过 12 项"）
  - 没测试？手动走关键路径，写明输入→输出（如"输入空列表返回空列表，与原行为一致"）
  - 改了边界处理？用空值/异常值实测并记录输入
- 涉及对外行为/接口变化时，同步更新注释或文档，并在输出中明确告知用户

## 输出
逐处改动清单，每项一行：

`[文件:行] [优先级] 问题 → 处理方式 → 验证方式与结果`

按 Must-Fix（P0）/ Should-Fix（P1–P2）/ Nice-to-Have（P3）分组，最后汇总验证结果与遗留风险（未处理项及其原因）。

## 红线（绝对不做）
- ❌ 不删看不懂的代码
- ❌ 不改没有测试覆盖的关键路径（先补测试或手动验证）
- ❌ 不为"更优雅"改接口签名、破坏行为兼容
- ❌ 不为小问题引入新依赖，也不主动升级已有依赖版本
- ❌ 不改 lint/格式化等工程配置（除非用户明确要求）
- ❌ 不顺手重构审查范围之外的代码；发现范围外问题只报告，不动手

## 示例对照
- ✅ 提取公共函数复用、删除重复片段、补空值与异常处理、每项改动附具体验证方式与结果
- ❌ 复制粘贴大段代码、保留无用导入/变量/死分支、忽视边界、未经验证就说完成、把风格差异当问题大改
