# 性能与内存：定位、取舍与验证

用于性能或内存优化，以及审查中发现的相关问题。按目标选择条目，普通清理无需执行整套性能分析；优先使用项目已有工具，不强制引入基准框架或监控设施。

## 先建立问题与基线

- 从真实工作负载确定目标：延迟、吞吐量、CPU、I/O 次数、内存峰值或长期保留量。记录典型及较大输入规模、并发量和已有预算；缺少目标时先测现状，不编造阈值。
- 沿实际热路径定位成本：重复扫描或排序、循环内不变计算、多余序列化和拷贝、数据库 N+1 或重复请求、阻塞操作、锁竞争。复杂度分析需说明输入规模与调用频率，不能把所有嵌套循环都认定为瓶颈。
- 先减少不必要的工作，再考虑数据结构、批处理、缓存或并发。简单且可证明的重复工作消除不必等待完整 profiling；收益不明却增加复杂度的优化，先取得热点或测量证据。

## 选择优化并说明代价

| 手段 | 适用依据与必要取舍 |
| --- | --- |
| 数据结构或算法调整 | 分析构建成本与查询频率，以及时间、空间、顺序、重复值和相等性语义；更低的渐进复杂度不保证小输入更快 |
| 缓存 / 记忆化 | 确认重复工作、命中机会和键语义；明确容量边界、淘汰或过期、失效条件及数据隔离，避免无限增长或陈旧结果 |
| 批处理 / 合并 I/O | 权衡往返次数、批次大小、峰值内存、等待时间、失败粒度与事务语义 |
| 流式 / 惰性处理 | 确认上下游不会再次全量物化；处理背压、取消和关闭，并检查顺序、异常时机与重复迭代语义 |
| 有界并发 / 并行 | 根据 CPU 或 I/O 瓶颈选择；考虑共享状态、任务开销、外部限额、队列上限及取消后的资源回收，避免无界创建任务 |
| 复用缓冲区 / 减少拷贝 | 先确认分配或复制是实际成本；检查所有权、别名和生命周期，防止数据被后续调用覆盖或长期保留大缓冲区 |

背压的作用是约束生产与消费速率不匹配时的数据积压，单纯改成异步并不能限制内存。参见 [Node.js 背压说明](https://nodejs.org/learn/modules/backpressuring-in-streams)；具体实现遵循当前语言和库的生命周期约定。

## 检查内存与资源生命周期

- 区分**分配量**（期间创建多少）、**保留量**（操作完成后仍存活多少）、**峰值**（最大同时占用）；区分语言堆、原生或外部内存与进程 RSS，使用同一指标比较前后。
- 检查所有者及释放时机：全局集合、缓存、闭包、订阅与监听器、定时器、后台任务、连接、文件、锁和缓冲区。成功、失败、提前返回和取消路径都应完成适用的清理；释放应由拥有该资源的一方负责。
- 查找无界队列、积累结果、全量加载、重复拷贝和意外保留的大对象。评估容量、存活时间及并发共同决定的峰值，而不只看单次调用。
- 在相同负载下重复“创建 → 使用 → 释放”，观察稳定阶段的保留趋势，结合堆快照、分配采样或引用链定位原因。区分一次性初始化、有限缓存预热、分配抖动与持续保留。
- 内存上涨或释放后 RSS 未立即下降，不能单独证明泄漏。运行时可能保留内存，分配器碎片也可能导致 RSS 增长；不要以强制 GC 或定时清空掩盖根因。

指标与排查依据：[Node.js `memoryUsage`](https://nodejs.org/api/process.html#processmemoryusage)区分堆、外部内存与 RSS，并说明碎片影响；[Chrome 内存排查](https://developer.chrome.com/docs/devtools/memory-problems)展示分配、保留引用与 GC 的诊断方式。使用这些原则，不把某个运行时的工具或数值阈值泛化到其他项目。

## 可复现地比较前后

- **固定条件**：记录代码版本、运行时、构建模式、硬件或资源限制、数据与输入规模、并发和测量命令；前后执行相同工作，并校验结果等价或符合预期修复。
- **处理状态**：区分冷启动与稳态，按目标处理 JIT、预热、缓存及 GC；每轮恢复需要重置的输入，避免后续轮次测到空数据或不同状态。消费测量结果，避免编译器消除工作。
- **重复并解释波动**：根据工具与工作负载重复测量，报告适当的统计值及波动，不凭单次计时或噪声范围内的差异宣布收益。不强制所有基准使用同一种统计口径。
- **同时检查代价**：改善延迟时检查吞吐和内存，降低峰值时检查 CPU 与 I/O 等相关指标；优先报告用户关心的端到端结果。微基准只支持被测片段的结论。
- **控制测量干扰**：性能采样和堆分析本身有开销，必要时与耗时基准分开运行；短时采样可能漏掉峰值，累计峰值指标比较时需独立运行或正确重置。
- **如实报告**：说明“环境与输入 → 前后值、单位与统计口径 → 结果及代价”。没有前后数据时，只能说明复杂度、操作次数或资源生命周期的推断与依据，并标注未实测，不能给出实际提速或内存下降比例。

测量方法参考：[Google Benchmark 用户指南](https://google.github.io/benchmark/user_guide.html)涵盖预热、重复运行、统计与测量优化陷阱；[Python `timeit`](https://docs.python.org/3/library/timeit.html)说明其默认关闭 GC 等工具特性。选择适合项目的工具，并确认默认行为没有排除要测量的成本。
